# ループエンジニアリングについて学ぶ

- https://addyosmani.com/blog/loop-engineering/
- https://zenn.dev/explaza/articles/d0aeb08fcd1888

## ループエンジニアリングとは
- エージェントハーネスエンジニアリング
  - これは単一のエージェントが内部で動作する環境とソフトウェアを構築するシステムであるファクトリーモデルを作成するもの
  - ループエンジニアリングはハーネスの一階層上に存在する

- 今までは人間がプロンプトを入力しAIが出力し人間が確認しまたプロンプトを打つという流れの「ターン制」が主流
- しかし現在では「人間に変わってエージェントを駆動する自動化されたループを設計(システム)を設計すること」になっている

- AnthropicのClaudeCode責任者も「Claudeに直接プロンプトを打っていない、Caludeを動かすループを走らせており私の仕事はループを描くことだ」と述べている

## ループの要素 5個+1個
- ループには5つの要素とそれらを記憶しておくメモリが必要

### 自動化
- スケジュールに基づいて自動的に起動し、検出とトリアージを行う自動化システム
- 具体的には
  - 定期的に（スケジュールやフック、GitHub Actionsなどで）起動し、CIエラーの要約やバグハンティング、Issueのトリアージを自律的に行う。条件が達成されるまで回り続ける

### ワークツリー
- ワークツリーを使用することで、2人のエージェントが並行して作業しても互いに干渉し合うことがなくなる
- 具体的には
  - 複数のAIエージェントが並行して動く際、同じファイルを同時に書き換えて衝突（コンフリクト）しないよう、git worktree等を用いて環境を完全に隔離する

### スキル
- エージェントが推測するにとどまるようなプロジェクトに関する知識を書き留めるスキル。
- 具体的には
  - エージェントが毎回プロジェクトの前提やルールを忘れないよう、SKILL.mdなどのファイルにビルド手順や「この設計は過去の障害から禁止」といった文脈（コンテキスト）をアセット化しておく

### ツールを接続
- エージェントを既存のツールに接続するためのプラグインとコネクタ
- 具体的には
  - MCP（Model Context Protocol）などを利用し、AIがファイルシステムだけでなく、GitHub、Linear（タスク管理）、Slack等と連携できるようにする。「修正コードを書き、PRを出し、Linearのチケットを更新してSlackに通知する」までを繋ぐ

### アイデアを出し、検証する
- サブエージェントなので、1人がアイデアを持ち、別のサブエージェントがそれを検証する
- 具体的には
  - コードを書くAI（Maker）自身にテストや検証をさせると、自分の間違いに気づきにくい（自分に甘くなる）。そのため、「実装するエージェント」と「検証・レビューするエージェント（Verifier）」を明確に分ける

### メモリ
- マークダウンファイルやリニアボードなど、単一の会話とは別に存在し、完了した内容と次に行うべき内容を保持するもの
- 具体的には
  - AIモデルはセッションごとにコンテキストを忘れてしまうため、何が完了し、何が次に必要なのかをAGENTS.mdやLinearのボードなど「ディスク上（外部）」に状態として保存しておく。
 
## ループが回る具体的なワークフローの例
著者が実際に活用している具体的なループの形は以下のようなもの

1. 毎朝、Automationがリポジトリで起動する
2. トリアージのSkillを使い、前日のCI失敗やIssueを読み込んでタスク化する
3. 修正すべきタスクごとに、隔離されたWorktreeを開く
4. 1つ目のSub-agentがコードを修正（実装）する
5. 2つ目のSub-agentがプロジェクトの共通ルール（Skills）やテストと照らし合わせてレビューする
6. パスすればConnector経由で自動でPRを作成し、タスク管理ツールを更新する

## ループエンジニアリングにおける「人間の役割」と新たな課題

AIが自律的にループしてコードを書きまくる時代になっても、エンジニア（人間）が不要になるわけではなく、むしろエンジニアの真価が問われるようになります。著者は以下の3つのリスク（負債）を警告している

- 検証責任（Verification）は人間に残る
- 理解の腐敗（Comprehension Debt / 理解債）
- 認知の放棄（Cognitive Surrender）

## 本質：楽になるのではない、レバレッジポイントが変わるの
著者のAddy Osmani氏がこの記事で最も伝えたかった本質は、「自動化ループにすべてを丸投げして楽をすることではない」ということ
提示された言葉の中に、私たちがこれからAIと向き合う上での重要な指針がすべて詰まっています。
ループは、使い方によって異なる結果をもたらす可能性がある

2人が全く同じループを作成しても、結果は正反対になることがあります。一方は、**深く理解している作業をより速く進めるためにループを使用し**、もう一方は、**作業内容を全く理解しないためにループを使用します**。
ループ自体はその違いを認識しないが、あなたは認識する。

自動化されたループは強力だが、人間がコードをレビューしなくなったり、修正をループだけに頼り切ったりすれば、製品の品質は間違いなく低下し、悪循環に陥ってしまう
時にはエージェントに直接プロンプトで指示を出す方が効果的な場面もあり、「適切なバランスを見つけること」が不可欠
**ループ設計がプロンプトエンジニアリングよりも難しいのは、まさにこの点にある。チェルニーの主張は、作業が楽になったということではなく、レバレッジポイントが変わったということ**

プロンプトのテクニックを磨く時代から、システム（ループ）を設計する時代へ。私たちの仕事の「レバレッジがかかる場所」が変わっただけで、エンジニアとしての思考や責任の重さは変わらない、むしろ難易度は上がっていると言える

## ループを構築せよ、エンジニアであり続けよ
この記事から得られる最大の学びは、これからのAI時代を生き抜くエンジニアのスタンスそのものです。
最後に、エンジニアの胸に刻むべき言葉として、以下のメッセージで締めくくられています。

**「ループを構築する。ただし、単にスタートボタンを押すだけの人間ではなく、エンジニアとして長く携わっていくつもりで構築するのだ。」**

AIという最強のループ（システム）を乗りこなしつつも、コードへの理解と品質への責任を手放さない。「スタートボタンを押すだけの人」に成り下がるな、という強い警鐘とエールを感じた

```sh
## 3. ループが回る具体的なワークフローの例（実例ベース）
「Loop Engineering」が実際にどう駆動するのか、著者が実践している一般的な1日の流れをベースに、具体的なタイムラインで追ってみましょう。

人間は寝ているか、別のクリエイティブな仕事をしている想定です。

【AM 7:00】自動起動と課題の発見（Automations & Skills）
裏側の動き： 毎朝7時、GitHub Actionsのタイマー、またはローカルPCのcronジョブによってループ（Claude Codeなどのセッション）が自動起動します。

具体アクション： 1. ループはまずプロジェクト固有のルールが書かれた SKILL.md（ビルド手順や「この設計はNG」という過去の知見）を読み込みます。
2. 次に、前日に発生した「CI（テスト）の失敗ログ」「GitHubの未対応Issue」「エラー監視ツールの通知」を自動でスクレイピングし、今日解決すべきバグのトリアージ（優先順位付け）をAIが行います。

【AM 7:15】並行作業環境の構築（Worktrees）
裏側の動き： トリアージの結果、「認証エラーのバグ」と「UIのレイアウト崩れ」の2つの課題が見つかりました。

具体アクション： * 1つのリポジトリ内でファイルが競合してクラッシュするのを防ぐため、ループは裏側で自動的に git worktree コマンドを実行します。

feature/fix-auth と feature/fix-ui という2つの独立した作業ディレクトリ（ブランチ）を別々のフォルダに一瞬で切り出し、並行して処理できる環境を整えます。

【AM 7:20】実装と、容赦ない身内レビュー（Sub-agents）
裏側の動き： ここがループエンジニアリングの最も強力な部分です。それぞれの作業ディレクトリに、役割の異なる「AIエージェントのチーム」が投入されます。

具体アクション：

エージェントA（実装担当 - Maker）： 「認証エラー」のコードをガリガリ修正します。

エージェントB（レビュー・検証担当 - Verifier）： 修正が終わると、実装担当とは別のモデル（思考力の高い大型モデルなど）が起動します。エージェントBは、Aが書いたコードに対して「本当にエッジケースを考慮しているか？」「既存のテストをパスするか？」を厳しくチェックします。テストが落ちたら、Aに突き返してループ内で修正をやり直させます。

※この「セルフチェック（/goal の達成確認）」が通るまで、AI同士で何度も修正とテストのループを繰り返します。

【AM 7:45】外部ツールとの連携と通知（Plugins & Connectors）
裏側の動き： AIチーム内でのレビューとテストがすべて合格（Green）になりました。

具体アクション：

ループはMCP（Model Context Protocol）などのコネクターを経由して、外部ツールへ一気にアクセスします。

自動でGitHubにPushしてPull Requestを作成し、タスク管理ツール（LinearやJira）のステータスを「レビュー待ち」に更新。さらに、Slackのチームチャンネルに「認証エラーの修正PRを作成しました。CIは通過済みです」と通知を飛ばします。

【AM 8:00】状態の保存（State / Memory）
裏側の動き： 次のループ（明日の朝や、数時間後の実行）のために、今回の進捗を記憶させます。

具体アクション：

AIのチャット履歴はセッションが切れれば消えてしまうため、ループはレポジトリ直下の AGENTS.md というMarkdownファイル、またはLinearのチケットに「何を試し、どのテストが通り、何が未解決か」をテキストとして書き出します（外部記憶の保存）。

【AM 9:00】人間のエンジニアが出社
あなたがコーヒーを片手に出社してPCを開くと、すでに「AIがテストを通し、身内レビューも済ませた、完璧なお膳立て済みのPR」が届いています。

ここから、この記事の核心である「人間による最終レビュー（本当にこのコードでいいのかのインスペクション）」という、最もレバレッジの高い仕事がスタートします。
```
